# 2. Кроссплатформенная система

[К содержанию](README.md) · [Назад: цели](01-goals.md) · [Далее: правила дизайна](03-design-system.md)

## 2.1. Основное архитектурное решение

### Рекомендуемый стек

- **Kotlin Multiplatform** — доменная модель, состояния, правила работы, файловый формат.
- **Compose Multiplatform** — общие продуктовые экраны.
- **Нативная оболочка Android** — жизненный цикл, системные окна, разрешения и интеграции.
- **Нативная оболочка iOS/iPadOS** — соответствующие возможности Apple.
- **SQLite и файлы в закрытом хранилище приложения** — постоянные локальные данные.
- **Платформенные речевые и аудиосредства** — синтез, воспроизведение, запись и аудиомаршрут.

Это **два самостоятельных устанавливаемых приложения**, использующих общую архитектуру. Между ними нет обязательного сетевого соединения.

### Почему это решение

В проекте уже используется Kotlin. При этом в 1.4 большая часть содержательного `shared` находится в `androidMain`, а общий `commonMain` почти пуст. Само название модуля ещё не делает систему кроссплатформенной.

Kotlin Multiplatform позволяет совместно определять:

- смысл карточек;
- правила составления сообщения;
- режимы общения;
- действия редактора;
- проверки файлов;
- состояния воспроизведения;
- условия сохранения и восстановления.

Общие экраны помогают не получить две разные продуктовые модели на Android и iOS.

Но системное поведение не маскируется под универсальный самодельный интерфейс: выбор файлов, разрешения, доступность и аудиосессия остаются платформенными.

### Почему не WebView как основа

Для согласованных двух мобильных платформ веб-оболочка не даёт достаточного преимущества, чтобы оправдать дополнительные связки для:

- речевых движков;
- записи;
- работы с файлами;
- системного фокуса;
- жизненного цикла;
- доступности сложной коммуникационной сетки.

Это не утверждение, что доступное веб-приложение невозможно. Здесь оно создаёт дополнительные риски без согласованной потребности в браузере.

### Главный риск общего UI

Общая разметка не гарантирует одинаковую доступность.

Compose Multiplatform предоставляет семантику, интеграцию с VoiceOver и поддержку клавиатуры, но:

- порядок обхода нужно определять;
- фокус нужно проверять на каждой платформе;
- высококонтрастную палитру нельзя считать автоматически решённой;
- сложные сетки нельзя объявлять доступными только потому, что кнопки построены стандартным компонентом.

**Общее поведение — цель. Формальное переиспользование любой ценой — нет.**

## 2.2. Что общее, а что платформенное

| Общее | Android / iOS отдельно |
|---|---|
| Доменная модель доски | Системный жизненный цикл |
| Команды и состояния общения | Аудиофокус и аудиосессия |
| Правила составления сообщения | Синтез речи |
| Правила редактора | Запись и воспроизведение аудио |
| Логическая структура страниц | Выбор изображения и файла |
| Проверка структуры импортируемого набора | Системные разрешения |
| Семантические роли элементов | Связь с системным фокусом и доступностью |
| Дизайн-токены | Safe areas, системные панели и клавиатура |
| Представление ошибок | Keychain / Keystore |
| Контракт локального хранения | Конкретный доступ к SQLite и файловой системе |

В общую модель не попадают:

- `Activity`;
- `Context`;
- `Uri`;
- `UIViewController`;
- `Bitmap`;
- платформенные проигрыватели;
- абсолютные пути файлов.

Общая модель знает о **медиа**, а не о том, как Android или iOS передают выбранный файл.

## 2.3. Доменная модель

### Основные термины

| Понятие | Смысл |
|---|---|
| **Библиотека** | Локальная упорядоченная коллекция досок |
| **Доска** | Подготовленное пространство выбора с содержимым и расположением |
| **Страница** | Логическая часть доски, а не случайная высота прокрутки |
| **Слот** | Определённое место на странице |
| **Карточка** | Смысловой элемент, который пользователь может выбрать |
| **Медиа** | Изображение или аудио, принадлежащее библиотеке |
| **Сообщение** | Последовательность выбранных элементов |
| **Сеанс общения** | Работа с конкретной доской и текущим сообщением |
| **Черновик** | Локально сохраняемое, но ещё не применённое изменение доски |
| **Ревизия** | Идентификатор опубликованного состояния доски |
| **Режим помощника** | Разрешённый контекст изменения библиотеки |

### Идентичность

Название доски не является её идентификатором.

В 1.4 имя архива одновременно участвует в идентификации и представлении. В целевой системе:

- у доски есть устойчивый `BoardID`;
- у карточки — `CardID`;
- у страницы — `PageID`;
- у медиа — `AssetID`;
- у слота — устойчивое положение в структуре страницы.

Переименование не должно:

- сбрасывать настройки;
- менять принадлежность черновика;
- терять сообщение;
- создавать новую доску;
- ломать ссылки на медиа.

### Карточка

У карточки разделены:

- видимая подпись;
- изображение;
- произносимое содержимое;
- способ произнесения.

Подпись «Пить» и произносимый текст «Я хочу пить» могут различаться. При этом приложение не придумывает за человека дополнительные слова.

Возможные способы произнесения:

1. Подготовленная аудиозапись.
2. Локальный синтез указанного текста.

Недоступность выбранного способа должна быть явным состоянием. Нельзя молча заменять запись другим текстом или произносить только часть сообщения, показывая полное успешное завершение.

### Пустой слот — не карточка

В текущей модели числовой `cardType` совмещает обычную карточку, пробел, пустое место и редакторский placeholder.

В целевой модели:

- пустой слот — отсутствие карточки;
- плюс «Добавить» — представление редактора;
- пробел — команда составления текста;
- содержательная карточка — отдельный доменный объект.

Редакторский placeholder не сохраняется как пользовательское содержимое.

### Режим общения и правила сборки — разные понятия

Нельзя одним флагом вроде `withoutSpace` неявно менять сразу несколько независимых правил.

Разделяются:

**Режим взаимодействия:**

- составление сообщения;
- немедленное произнесение выбранной карточки.

**Правило сборки текста:**

- слова с разделителями;
- буквальная последовательность символов с явными пробелами.

**Способ произнесения:**

- последовательность подготовленных записей;
- синтез результирующего текста.

Импорт старого набора сохраняет его прежний смысл, но внутри системы эти решения больше не склеены одним техническим флагом.

### Объём сообщения

Для базовой архитектуры сообщение связано с конкретной доской, как в обследованном сценарии 1.4.

Междосочное составление единой фразы здесь не добавляется незаметно. Оно меняет семантику сеанса и требует отдельного продуктового решения.

## 2.4. Главные инварианты

1. **Общение не требует разрешения помощника.**
2. **Доска, используемая для общения, имеет определённую опубликованную ревизию.**
3. **Редактирование черновика не меняет эту ревизию до применения.**
4. **Карточки не переставляются автоматически.**
5. **Изменение подписи не меняет идентичность карточки.**
6. **Незавершённая запись не становится готовым аудио.**
7. **Проигрывание начинается только вследствие явного действия пользователя.**
8. **Восстановление приложения не повторяет речь автоматически.**
9. **Неудачный импорт не повреждает существующую библиотеку.**
10. **Неудачное сохранение не заменяет рабочую доску частично записанной.**
11. **Кэш не является единственной копией пользовательских данных.**
12. **Пароль помощника не попадает в переносимый набор.**
13. **Ошибка одного набора не делает недоступными остальные.**

## 2.5. Модули системы

Система строится из нескольких глубоких модулей: небольшая понятная поверхность взаимодействия скрывает сложные правила внутри.

| Модуль | Ответственность | Что скрывает |
|---|---|---|
| **Communication** | Сеанс, сообщение, выбор, исправление, страницы | Правила двух режимов и восстановление состояния |
| **Library** | Опубликованные доски и устойчивый порядок | Идентичность, ревизии, сохранение и ссылки на медиа |
| **Authoring** | Черновики досок и карточек | Незавершённые изменения, валидацию, конфликты применения |
| **Audio** | Речь, воспроизведение, запись | Платформенные движки, очереди, прерывания и владение аудио |
| **Portability** | Импорт, экспорт и резервные копии | Архивы, проверки, преобразования и ограничения совместимости |
| **Access** | Разрешение защищённых действий | Локальную проверку и время жизни режима помощника |
| **Preferences** | Пользовательские настройки | Типизированное хранение и различие общих/досочных параметров |

Пользовательский интерфейс не обязан знать:

- как устроен ZIP;
- где находится запись;
- какой callback вернул речевой движок;
- можно ли уже удалить временный файл;
- сохранена ли последняя версия карточки в архиве.

Эти знания должны находиться в одном месте, а не повторяться в каждом экране.

### Ограничения зависимостей

- Интерфейс не обращается к файловой системе напрямую.
- Communication не зависит от редактора.
- Доменная модель не зависит от Compose.
- Платформенные адаптеры исполняют запросы, но не определяют продуктовый смысл.
- Импорт не имеет отдельного обходного пути записи в библиотеку.
- Проверка разрешений применяется к защищённой команде, а не только к видимости кнопки.

Отдельный модуль не означает отдельный процесс, сервер или десятки библиотек.

## 2.6. Состояния общения

### Режим составления сообщения

| Действие | Результат |
|---|---|
| Выбрать карточку | Добавить один элемент |
| Повторно выбрать ту же карточку | Добавить ещё один элемент: повтор может быть осмысленным |
| Удалить последний элемент | Удалить именно последний выбранный элемент |
| Очистить | Очистить сообщение с возможностью отменить действие |
| Произнести | Произнести зафиксированный снимок сообщения |
| Переключить страницу | Сохранить сообщение |
| Уйти с доски | Остановить звук, сохранить черновик сообщения |
| Восстановить приложение | Восстановить последний сохранённый снимок без автоматической речи |

### Поведение при активной речи

Для озвучивания фиксируется снимок сообщения и идентификатор запроса.

| Действие во время речи | Поведение |
|---|---|
| Нажать «Остановить» | Остановить текущий запрос |
| Добавить карточку | Остановить речь, затем изменить сообщение |
| Удалить элемент | Остановить речь, затем удалить элемент |
| Очистить сообщение | Остановить речь, затем очистить |
| Переключить страницу | Не менять произносимый снимок |
| Закрыть доску | Остановить речь |
| Получить запоздалый callback старого запроса | Игнорировать его |

Кнопка «Произнести» во время воспроизведения становится **«Остановить»**, а не остаётся неоднозначной кнопкой с тем же значком.

### Прямой режим

- Выбор A начинает произнесение A.
- Выбор B останавливает A и начинает B.
- Повторный выбор A — явный повтор, а не технический дубль.
- Не образуется скрытая очередь десятков касаний.
- Ошибка не вызывает автоматического повторного произнесения.

Это особенно важно для AAC: повторить сообщение без запроса пользователя — не нейтральная техническая операция.

### Клавиатурный ввод

Различаются:

- удаление карточки из карточного сообщения;
- удаление символа из буквального текста.

Для текста удаляется пользовательский символ, а не произвольная часть UTF-16. Эмодзи, комбинируемые знаки и другие составные символы не должны ломаться.

Автокоррекция не меняет смысл сообщения без явно включённой пользователем функции.

## 2.7. Редактор и черновики

### Опубликованная доска и черновик разделены

Общение использует опубликованную доску.

Редактор работает с отдельным черновиком:

- изменения сохраняются локально;
- исходная доска остаётся пригодной для общения;
- применение черновика создаёт новую опубликованную ревизию;
- закрытие редактора не означает молчаливое удаление работы.

### Семантика действий

- **«Сохранить карточку»** — принять карточку в черновик доски.
- **«Применить изменения»** — опубликовать черновик доски.
- **«Закрыть редактор»** — оставить сохранённый черновик.
- **«Удалить черновик»** — отдельное разрушительное действие.

Не используется двусмысленное «Выйти из сохранения».

Автосохранение черновика не должно выглядеть как уже применённое изменение рабочей доски. Статусы различаются:

- «Черновик сохраняется»;
- «Черновик сохранён»;
- «Изменения применены»;
- «Не удалось сохранить черновик».

### Состояния черновика

`Открыт → Изменён → Сохраняется → Сохранён`

Отдельно:

- ошибка сохранения;
- применение;
- конфликт ревизий;
- удаление черновика.

Ошибка не превращает черновик в «готово» и не закрывает редактор автоматически.

### Конфликт ревизий

Даже без сервера возможны два окна или два экземпляра редактора одной доски.

Черновик знает исходную ревизию. Если рабочая доска уже изменилась, применение не использует молчаливое «последний сохранивший победил».

Допустимые результаты:

- сохранить отдельную копию;
- открыть актуальную версию для сравнения;
- отменить применение, сохранив черновик.

### Незавершённые медиа

Состояния записи:

`Нет записи → Запрашивается разрешение → Записывается → Завершается → Готова`

Отдельно:

- отказ в разрешении;
- прерывание;
- ошибка;
- отмена.

Запись, прерванная уходом приложения в фон или системным событием, не считается готовой только потому, что на диске появился файл.

## 2.8. Аудио и настоящая автономность

### Два разных обещания

**Доступность данных без сети** не равна **доступности синтеза речи без сети**.

Наборы могут находиться на устройстве, но подходящий голос может:

- не быть установлен;
- требовать загрузки;
- отсутствовать для языка;
- зависеть от выбранного Android-движка.

Поэтому Audio предоставляет состояние возможностей:

- готов к локальному синтезу;
- голос не установлен;
- язык недоступен;
- движок инициализируется;
- аудиовыход прерван;
- ошибка воспроизведения.

### Правила offline

- Подготовленные записи проигрываются локально.
- Синтез использует только подходящий локальный голос.
- Сетевой голос не подставляется незаметно.
- Первоначальная загрузка голоса системой не выдаётся за уже выполненное условие offline.
- При отсутствии голоса сообщение остаётся видимым.
- Пользователь получает конкретное объяснение проблемы, а не общую ошибку «не получилось».

На Android существует признак `Voice.isNetworkConnectionRequired()`. Он полезен для выбора голоса, но не заменяет проверку фактической работы без сети на поддерживаемых движках.

### Один владелец аудио

В приложении один координатор аудио.

Он согласует:

- произнесение сообщения;
- воспроизведение отдельной карточки;
- предпрослушивание в редакторе;
- запись микрофона.

Несколько экранов не создают независимые проигрыватели, конкурирующие за динамик.

У каждого запроса есть владелец и идентификатор. Закрытый редактор не может поздним callback изменить состояние нового сеанса.

### Системные события

| Событие | Контракт |
|---|---|
| Телефонный звонок / системное прерывание | Остановить или прервать согласно платформе, не повторять речь самостоятельно |
| Отключение наушников | Не продолжать незаметно произносить личное сообщение новым маршрутом |
| Уход в фон | Не считать приложение гарантированно работающим дальше |
| Возвращение | Показать состояние, не запускать прежнее сообщение автоматически |
| Потеря движка | Сохранить сообщение и сообщить причину недоступности |
| Успех старого запроса после отмены | Не менять актуальное состояние |

TalkBack и VoiceOver не отключаются приложением. Чтение названия системным средством доступности не равнозначно отправке сообщения собеседнику.

## 2.9. Постоянное хранение

### Структура

SQLite хранит:

- идентичность и порядок досок;
- актуальную ревизию;
- структурированные документы досок;
- черновики;
- сведения о медиа;
- настройки.

Файловое хранилище содержит:

- изображения;
- аудио;
- временно подготовленные импортируемые материалы.

Кэш содержит только то, что можно восстановить:

- миниатюры;
- уменьшенные изображения;
- производные предпросмотры.

### Почему не ZIP как рабочая база

ZIP удобен для обмена, но не обязан быть рабочим хранилищем редактора.

Постоянная работа через распаковку и перепаковку усложняет:

- частичное редактирование;
- сохранность;
- управление временными файлами;
- идентичность;
- восстановление;
- конкуренцию двух редакторов.

В целевой системе ZIP — переносимый документ, а не скрытая замена локальной базе данных.

### Атомарность

Транзакция SQLite сама по себе не делает файловые изменения атомарными.

Контракт публикации:

1. Новые медиа полностью подготовлены в закрытом хранилище.
2. Существующие используемые медиа не перезаписываются.
3. Короткая транзакция публикует новые ссылки и ревизию доски.
4. Только после этого состояние считается применённым.
5. Неиспользуемые временные файлы могут быть очищены отдельно.

При сбое до публикации рабочая доска остаётся прежней. После публикации она не ссылается на ещё не подготовленный файл.

Это правило архитектуры сохранения, а не план внедрения.

### Очистка

Медиа нельзя удалять, пока на него ссылается:

- опубликованная доска;
- сохранённый черновик;
- незавершённая операция, которая вправе его опубликовать.

Очистка координируется с записью. Фоновая уборка не может гонкой удалить материал активного импорта.

### Восстановление сообщения

Сообщение сохраняется как небольшой локальный снимок:

- доска;
- ревизия;
- последовательность элементов;
- страница.

Сохранение не откладывается только на `onStop`: ОС может завершить процесс без удобного завершающего события.

Восстанавливается последний успешно записанный снимок. Нельзя обещать сохранность ещё не завершённой записи или последнего изменения, которое не успело зафиксироваться.

## 2.10. Форматы, импорт и перенос

### `.linka` остаётся пользовательским контрактом

Старые наборы нельзя считать расходным материалом.

Импорт:

- не меняет исходный файл;
- сохраняет порядок;
- сохраняет пустые места;
- сохраняет назначение пробела;
- сохраняет подписи и подготовленные записи;
- не объединяет доски только по совпадению названий.

Новые внутренние идентификаторы не обязаны совпадать со старыми числовыми `id`.

### Проверка файла

Импорт — недоверенный ввод, даже если файл пришёл от знакомого человека.

До публикации проверяются:

- структура архива;
- схема документа;
- версия;
- размеры и количество элементов;
- относительные пути;
- отсутствие выхода из рабочей области;
- отсутствие опасных ссылок и конфликтующих имён;
- фактический распакованный объём;
- размеры изображений;
- существование указанных медиа;
- возможность обработать необходимые форматы.

Валидация JSON без проверки медиа не означает успешный перенос.

### Совместимость аудио

Старый Android-код записывает `.3gpp` с AMR-NB. Нельзя автоматически считать, что каждый такой файл одинаково обработается средствами iOS.

Архитектурный контракт:

- импорт проверяет фактическое декодирование;
- новые записи используют согласованный переносимый формат;
- для неподдерживаемого старого кодека требуется проверенный локальный способ обработки;
- иначе выдаётся точное ограничение, а не успешный импорт с пропавшим голосом.

Поддержка всех старых медиа на iOS — **непроверенная предпосылка**, которую нельзя скрыть словом «кроссплатформа».

### Экспорт набора и резервная копия — разные вещи

**Экспорт набора** переносит одну доску.

**Полная резервная копия** сохраняет библиотеку и необходимые пользовательские настройки.

В интерфейсе нельзя называть экспорт одной доски полной резервной копией приложения.

Пароль помощника и платформенные секреты не включаются в обычный переносимый набор.

### Совместимость со старым приложением

| Направление | Требование |
|---|---|
| Старый `.linka` → новая система | Поддерживаемый импорт с сохранением смысла |
| Новая доска → старый формат | Только если содержимое представимо без незаметной потери |
| Новый способ речи → старый читатель | Нельзя объявлять совместимость, если старому приложению нужен отсутствующий аудиофайл |
| Неизвестная версия резервной копии → приложение | Явный отказ без частичной замены библиотеки |
| Старый бинарник → новая внутренняя база | Не обещается как безопасный откат |

**Откат приложения не равен откату данных.** Автоматическое удаление базы при несовпадении схемы недопустимо.

## 2.11. Приватность и защита редактирования

### Локальность

В целевой системе нет:

- отправки сообщений на сервер;
- аналитики содержимого фраз;
- загрузки записей;
- обязательного рекламного или аналитического SDK;
- удалённого профиля пользователя.

Диагностические журналы не содержат текст сообщений, пароль и содержимое аудио.

Если человек сам выбрал iCloud Drive, Google Drive или системную отправку файла, данные могут покинуть устройство через выбранное им средство. Это не скрытая синхронизация приложения.

### Режим помощника

Это защита от случайного или нежелательного изменения, а не обещание абсолютной защиты от владельца разблокированного устройства.

Проверяются команды:

- редактирования;
- удаления;
- замены;
- изменения критических настроек;
- импорта с изменением библиотеки;
- выдачи данных наружу, если включена соответствующая защита.

Скрытая кнопка не заменяет проверку команды.

### Пароль

- Не хранится открытым текстом.
- Проверяется по устойчивому локальному верификатору.
- Связанные секреты защищаются средствами платформы.
- Доступ не восстанавливается из сохранённого UI-состояния.
- Восстановление доступа не требует уничтожить наборы.
- Включение защиты без законченной настройки не создаёт ловушку.

Общение продолжает работать, даже если помощник забыл пароль.

### Разрешения

Микрофон запрашивается при начале записи, а не при первом запуске.

Файлы и фотографии выбираются системными средствами с минимально необходимым доступом.

Отказ в разрешении не блокирует:

- использование существующих карточек;
- чтение сообщения;
- синтез речи, которому это разрешение не нужно.

## 2.12. Архитектурные свойства качества

### Быстродействие

- Реакция выбора отображается немедленно, без ожидания аудиодвижка.
- Декодирование изображений и архивов не занимает UI-поток.
- Для сетки используются изображения подходящего размера.
- Не загружается вся библиотека полными bitmap.
- Подготовка следующей страницы ограничена и не вытесняет текущую.
- Инициализация речи не мешает визуальному общению.

Проектный ориентир для реакции выбора — до 100 мс на целевых устройствах. Задержка начала речи измеряется отдельно и зависит от движка и медиа.

### Доказуемые свойства

Архитектура должна позволять проверить без настоящего динамика:

- одинаковую реакцию на команды на обеих платформах;
- отмену старого запроса;
- отсутствие автоматической речи после восстановления;
- сохранение сообщения при переключении страниц;
- изоляцию черновика;
- конфликт ревизий;
- отказ от опасного импорта.

А на устройствах отдельно проверяются:

- реальные аудиопрерывания;
- клавиатура;
- фокус;
- TalkBack и VoiceOver;
- размеры текста;
- отсутствие сети;
- поведение системных окон.

Поддержка Android 5.0 в 1.4 — установленный факт старой версии, но не автоматически выбранный минимум нового стека. Минимальные версии Android и iOS должны быть явным продуктовым контрактом; тихо исключать старые устройства нельзя.
