# 3. Правила дизайна

[К содержанию](README.md) · [Назад: кроссплатформенная система](02-cross-platform.md) · [Далее: C4](04-c4.md)

## 3.1. Главный принцип

> Интерфейс должен уменьшать усилия на выражение мысли, а не демонстрировать устройство приложения.

В режиме общения человек видит прежде всего:

1. доступные элементы;
2. текущее сообщение;
3. действие произнесения;
4. понятное исправление.

Настройки, структура файлов и технические параметры вторичны.

## 3.2. Два пространства работы

### Пространство общения

- доска;
- сообщение;
- произнесение / остановка;
- удаление последнего элемента;
- очистка;
- переход между страницами и досками.

### Пространство помощника

- библиотека;
- редактор;
- параметры расположения;
- изображения и звук;
- импорт / экспорт;
- резервные копии;
- настройки.

Это не два аккаунта и не два приложения. Это разные контексты с разными рисками.

Режим редактирования явно обозначен. Сетка без шапки не должна выглядеть так, будто случайное касание сейчас произнесёт карточку, когда на самом деле оно её изменяет.

## 3.3. Информационная структура экранов

| Экран | Основное действие | Что не должно отвлекать |
|---|---|---|
| Библиотека | Открыть доску | Технические имена файлов |
| Доска | Выбрать и выразить сообщение | Параметры сетки |
| Редактор доски | Подготовить расположение и применить изменения | Постоянные повторные подтверждения |
| Карточка | Задать смысл, изображение и речь | Неподписанные поля и скрытые требования |
| Импорт | Проверить и добавить набор | Случайная замена существующего |
| Резервные копии | Сохранить или восстановить библиотеку | Путаница с экспортом одной доски |
| Настройки | Изменить понятное свойство | Технические термины и длинные строки |

## 3.4. Компоновка доски

Доска состоит из независимых областей:

- компактная навигация;
- постоянная область сообщения;
- постоянные коммуникационные действия;
- рабочая область сетки;
- пагинация при необходимости.

### Обязательные правила

- Сообщение не уезжает вместе со всей сеткой.
- Произнесение не исчезает из-за прокрутки.
- Длинное сообщение прокручивается внутри своей области.
- Добавление карточки не вызывает неограниченного роста шапки.
- Системная жестовая область не перекрывает нижний ряд.
- Экранная клавиатура не закрывает редактируемое поле и подтверждение.
- Альбомная ориентация не навязывается всему приложению.

### Пространственная стабильность

Логическая страница и визуальная раскладка — не одно и то же.

Приложение не должно незаметно:

- сортировать карточки по популярности;
- менять порядок после обновления;
- переносить элементы по новым колонкам при небольшом изменении окна;
- сдвигать пустые места;
- менять знакомые изображения.

Когда сохранённая сетка не помещается с допустимыми размерами:

- нельзя бесконечно уменьшать элементы;
- допускается управляемый просмотр сетки;
- используется заранее определённая компоновка, если она подготовлена помощником;
- изменение расположения должно быть явным, а не случайным результатом адаптивной сетки.

Для библиотеки допустима более свободная адаптация колонок. Для моторно освоенной доски нужна более строгая стабильность.

## 3.5. Телефон и планшет

| Ситуация | Решение |
|---|---|
| Телефон, общение | Компактная навигация, максимальная полезная площадь карточек |
| Телефон, редактор карточки | Полноценная форма, не несколько вложенных диалогов |
| Планшет, общение | Использовать место для читаемости, а не только увеличивать пустые поля |
| Планшет, редактор | Допустимо соседство параметров и предпросмотра |
| Очень узкое окно | Сохранить минимальные цели касания и доступность основных действий |
| Крупный шрифт | Увеличить пространство / изменить представление, не обрезать смысл |
| Мышь и клавиатура | Те же действия без обязательного касания |

Адаптация определяется доступным окном и возможностями ввода, а не только признаком «планшет».

## 3.6. Карточка

### Визуальная структура

Карточка имеет:

- различимое изображение или текстовое содержимое;
- читаемую подпись;
- достаточную цель активации;
- понятный фокус;
- различимое состояние нажатия.

Подпись не накладывается на произвольную фотографию без гарантированного фона.

Не используется текст, заранее нарисованный в bitmap, как основной способ отображения подписи. В 1.4 это прямо видно в `GridButton`: подпись превращается в изображение. Такой подход мешает масштабированию и семантической доступности.

### Размеры

Минимальные платформенные ориентиры:

- Android — цель касания не меньше 48 dp;
- iOS — ориентир 44 pt.

Для коммуникационных карточек эти значения — **нижняя граница, а не желаемый размер**. На практике могут потребоваться существенно более крупные элементы.

Размер определяется потребностями человека и количеством элементов. Нет одного универсального числа для всех пользователей AAC.

### Текст

- Не использовать многоточие там, где оно скрывает смысл карточки.
- Не уменьшать длинное название до нечитаемого размера.
- Разрешать перенос в пределах предсказуемого контейнера.
- Не дублировать символ мелкой копией без полезной причины.
- Сохранять исходный регистр и язык содержимого.
- Не превращать обычную подпись в декоративную картинку.

### Изображение

- Изображения сохраняют пропорции.
- Важные части не обрезаются ради заполнения плитки.
- Пользовательские фотографии не заменяются автоматически.
- Фон и рамка могут быть согласованы, не меняя знакомый символ.

## 3.7. Сообщение и произнесение

### Карточное сообщение

Выбранные элементы должны быть достаточно крупными, чтобы человек мог проверить результат.

Большая кнопка произнесения рядом с почти нечитаемыми миниатюрами — плохой баланс.

### Текстовое сообщение

Текст:

- визуально отделён от кнопок;
- не выглядит неактивным;
- не обрезается без возможности просмотра;
- остаётся доступным при смене страницы символов.

### Действия

Используются разные названия:

- «Произнести»;
- «Остановить»;
- «Удалить последнее»;
- «Очистить сообщение».

Одна и та же иконка крестика не обозначает одновременно закрытие, очистку и удаление объекта.

Очистка сообщения и удаление подготовленной доски имеют разные последствия и разную защиту.

## 3.8. Касание, мышь и клавиатура

### Касание

- Активация по завершённому касанию.
- Начатое касание можно отменить уходом за пределы цели.
- Долгое нажатие не является единственным способом открыть важное действие.
- Перетаскивание не является единственным способом изменить порядок.
- Непреднамеренный повтор ввода не исправляется грубым запретом осмысленных повторов.

### Мышь

- Наведение не произносит карточку.
- Значимые действия доступны без hover.
- Указатель и фокус не скрывают подпись.
- Правый клик, если поддерживается, не заменяет видимую команду.

### Клавиатура

- Есть понятный порядок Tab.
- Внутри сетки доступна пространственная навигация.
- Активация не возникает от одного получения фокуса.
- Системные комбинации не перехватываются без необходимости.
- В текстовом поле пробел остаётся пробелом.
- Удержание клавиши не создаёт непредсказуемую очередь произнесения.
- Escape не уничтожает черновик целиком.

Системный Full Keyboard Access на iPadOS и поведение TalkBack/VoiceOver учитываются отдельно. Нельзя считать, что обработка нескольких клавиш заменяет полноценный системный доступ.

## 3.9. Семантика и доступность

Каждая карточка предоставляет:

- имя;
- роль;
- состояние;
- действие.

Например:

> «Пить. Карточка. Добавить в сообщение».

А в прямом режиме:

> «Пить. Карточка. Произнести».

При этом изображение и подпись не должны зачитываться как два независимых одинаковых элемента.

Также необходимы:

- видимый клавиатурный фокус;
- устойчивый порядок обхода;
- корректный возврат фокуса после закрытия окна;
- названия для иконок;
- доступное сообщение об ошибке;
- отсутствие ловушек фокуса;
- уважение уменьшения анимации;
- поддержка крупного текста;
- отдельная высококонтрастная палитра.

Стандартная библиотека компонентов облегчает это, но не подтверждает соответствие автоматически.

## 3.10. Цветовая система

Предлагается сохранить бирюзовый характер приложения, но убрать зависимость значимости от жёлтого текста на белом.

### Базовая светлая палитра

| Назначение | Цвет |
|---|---|
| Основной акцент | `#006A6A` |
| Текст на акценте | `#FFFFFF` |
| Фон | `#F7FAFA` |
| Поверхность | `#FFFFFF` |
| Основной текст | `#172B2B` |
| Вторичный текст | `#435B5B` |
| Различимые границы | `#6C8585` |
| Опасное действие | `#B42318` |

Расчётные контрасты непрозрачных пар:

- белый на основном акценте — **6,42:1**;
- основной текст на белом — **14,82:1**;
- вторичный текст на белом — **7,28:1**;
- белый на опасном действии — **6,57:1**;
- граница `#6C8585` на белом — **3,94:1**.

Это проверка конкретных пар, а не сертификат доступности всего интерфейса.

### Правила применения

- Цвет не является единственным признаком опасности.
- Выбранность обозначается также рамкой/формой.
- Фокус отличается от выбранности.
- Ошибка содержит текст.
- Цвет содержимого карточки не обязан совпадать с цветом действия.
- Системная высококонтрастность поддерживается отдельными токенами.
- Тёмная тема имеет собственные проверенные пары, а не механическую инверсию.

## 3.11. Типографика и плотность

- Продуктовый текст отображается как текст.
- Размеры учитывают системное масштабирование.
- Подпись карточки и обычная инструкция имеют разные задачи и не обязаны иметь одинаковый размер.
- На планшете ограничивается длина строк форм и объяснений.
- В режиме общения нет длинных абзацев, которые нужно читать перед каждым действием.
- Настройка плотности не должна создавать цели меньше доступного минимума.
- При увеличении текста система не скрывает подтверждение и не перекрывает фокус.

Не следует копировать штатную шкалу типографики без оценки конкретного AAC-сценария.

## 3.12. Формы и диалоги

### Форма карточки

Содержательные блоки:

1. Смысл и подпись.
2. Изображение.
3. Произносимое содержимое.
4. Способ речи.
5. Проверка результата.
6. Принятие в черновик.

Не требуется заполнять изображение, текст и запись одновременно только ради прохождения общей проверки. Текстовая карточка с рабочим синтезом — полноценный вариант.

### Диалоги

Диалог подходит для короткого решения, а не для целого редактора.

Правила:

- назвать объект;
- назвать последствие;
- использовать глагол действия;
- не ставить «Готово» на удаление;
- не подтверждать безопасное действие ещё раз без новой информации;
- не создавать цепочку одинаковых модальных окон.

Примеры правильных формулировок:

- «Удалить набор „Еда“?»
- «Заменить существующий набор?»
- «Изменения сохранены в черновике».
- «Не удалось записать звук: доступ к микрофону запрещён».

## 3.13. Ошибки и восстановление

Ошибка сообщает:

1. Что не удалось.
2. Что сохранено.
3. Что человек может сделать.
4. Повлечёт ли действие потерю данных.

Примеры:

> «Не удалось применить изменения. Рабочая доска не изменена, черновик сохранён».

> «Этот голос недоступен без интернета. Сообщение осталось на экране».

> «Файл не добавлен: внутри набора отсутствует изображение карточки „Пить“».

Нельзя ограничиваться исчезающим Toast для ошибки, после которой пользователь не понимает, сохранилась ли его работа.

## 3.14. Содержимое и этика

- Нет автоматической замены знакомых карточек «более современными».
- Нет детского оформления по умолчанию для всех.
- Нет оценки «правильности» пользовательского сообщения.
- Нет наград за количество произнесённых фраз.
- Нет скрытого сбора содержимого общения.
- Нет автоматического произнесения при открытии экрана.
- Настройки не предполагают, что помощник всегда важнее основного пользователя.

Результат редизайна должен делать собственный голос человека доступнее, а не делать приложение заметнее его сообщения.
